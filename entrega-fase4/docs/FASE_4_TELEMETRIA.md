# Telemetría

Arduino → USB/Serial → Worker .NET 10 en PC → HTTPS (HTTP loopback explícito solo para desarrollo) → Gateway → Monitoring → SQL Server → evaluación Java → eventos/SignalR existente → Angular. No hay hub ni servicio IoT paralelo.

POST público `/api/monitoring/telemetry` se traduce a `/api/v1/monitoring/telemetry`. Es público respecto de JWT humanos y exige `X-Device-Token`. El servidor compara SHA-256 de la credencial en tiempo constante y limita deviceId, sensorId, estado y source por configuración `Telemetry:Devices`. Un JWT administrador por sí solo no permite publicar. Registrar una credencial aleatoria de al menos 32 caracteres por dispositivo; rotación mediante reemplazo del archivo privado y hash del servidor, reiniciando ambos. No existe renovación automática: 401/403 detienen envíos, preservan pendientes y exigen corrección.

DTO: readingId UUID, sensorId UUID, deviceId, value decimal con cuatro decimales como máximo, unit C, measuredAt UTC, source SIMULATED/ARDUINO. Valor por defecto permitido -55..150 °C configurable en Telemetry. Fecha entre hace siete días y cinco minutos futuros. Se verifica sensor activo de temperatura, comunidad derivada del catálogo y unidad compatible. El vínculo se mantiene en configuración validada por catálogo al recibir; no se crea otra entidad Sensor.

SQL: migración `20261029000100_Phase4Telemetry` agrega Source (históricos SIMULATED), DeviceId y TelemetryDispatched. El UUID de lectura es clave primaria y la inserción usa transacción serializable. Repetir el mismo UUID/datos devuelve la misma lectura sin eventos nuevos; cambiar los datos devuelve 409. Conflictos de concurrencia SQL pueden producir 5xx transitorio, reintentable por el puente. No reinicializar bases ni borrar volúmenes.

Monitoring confirma recepción después de persistir. Un worker consulta pendientes y usa el evaluador de alertas existente, que deduplica por readingId. Después publica SensorReadingUpdated en el hub existente y marca despachado. Fallos conservan pendientes y reintentan cada dos segundos. Entrega al menos una vez: SignalR puede repetirse si cae el proceso antes del último commit; Angular hace upsert/consulta REST. No promete entrega de cada evento a clientes desconectados; REST sincroniza el estado y el histórico.

Puente: ISerialDataSource, BackgroundService, DI, IHttpClientFactory, CancellationToken, DTOs y opciones validadas. SQLite WAL conserva UUID/payload antes de enviar, elimina confirmados, FIFO, backoff de 2 a 64 segundos. 429/5xx/red reintentan; 4xx permanentes se registran y eliminan; 401/403 detienen envío y retienen buffer. Retención por antigüedad measuredAt se aplica al despachar, con error explícito por cada vencimiento. MaxReadings limita filas, y frames seriales a 4096 caracteres. Se permite crecimiento de archivos WAL por operación normal; SQLite recupera/reutiliza páginas, no es una cuota exacta de bytes. No ejecutar dos puentes con el mismo archivo de cola.

Los sensores asociados se excluyen del simulador servidor y de inserción manual; el resto sigue simulado. Si la asociación está inactiva se rechaza ingestión y se mantiene exclusión, evitando que el simulador aparente datos físicos frescos. Chart agrupa por bucket y source. El panel distingue línea física verde y simulada discontinua, selecciona sensor/comunidad y recupera REST cada cinco segundos además de SignalR. Ningún valor aleatorio se genera en Angular.

No se modificaron manifiestos Kubernetes. El responsable deberá inyectar Telemetry y OAUTH_* en configuraciones existentes cuando se autorice infraestructura, con HTTPS público y Secrets reales.
